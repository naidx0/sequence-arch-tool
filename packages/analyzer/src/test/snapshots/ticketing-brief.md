# Scaffolding brief: ticketing

Generated by `sequence scaffold-brief` from a design-mode architecture spec.
Execute every rule below exactly — they are what make the scaffold a faithful,
runnable implementation of the spec.

**What conformance actually checks.** `sequence diff` compares each edge as
service-pair + direction + kind, where kind is one of `http`, `queue_publish`,
`queue_consume`, `db_access` (only `db_read`/`db_write`/`db_access` collapse to
`db_access`; publish vs consume ARE distinguished). On top of that, for a
design-mode spec it now **also** compares detail: HTTP **method and path**, and
DB **table name** — wiring the wrong method, path, or table is reported as
"Wrong wiring details" and fails the diff (exit 3). Matching is tolerant: an
unspecified or wildcard field on either side (a `*` path segment, an omitted
method) imposes no constraint, and path shapes are compared structurally so
`/tickets/{id}`, `/tickets/:id` and `/tickets/*` are equivalent. Queue topics
are already identified by the edge itself, so there is no extra topic detail to
check. Follow every rule below: the method, path, and table ones are now gated.

## The law

1. **Naming law.** Service directories and compose service names are the spec
   labels **verbatim** (no prefixes/suffixes/case changes). Topic strings in
   code are the topic labels **verbatim**, as inline string literals at every
   publish/subscribe call site — no constants, no config indirection.
2. **Env var law.** Cross-service wiring uses exactly these env var names,
   declared in `docker-compose.yml` `environment:` blocks (nowhere else):
   `<TARGET_LABEL_UPPERCASED>_URL` for HTTP (non-alphanumerics become `_`),
   `DATABASE_URL` for the database, `REDIS_URL` for the broker.
3. **Port law.** Python/fastapi services listen on 8000; TypeScript services
   listen on 3000. HTTP env wires point at `http://<label>:<port>`. An
   entry-point service (runs an HTTP server AND is called by nothing else in
   the spec) also publishes its port to the host as `"<port>:<port>"` so real
   traffic can reach it; internally-reached services need no host mapping.
4. **No extra cross-service calls.** Any HTTP call, queue operation, or SQL
   statement reaching another service that is not listed below is a defect.
   A local `GET /health` route per service is allowed (it produces no edge),
   but never call another service's health endpoint.
5. **Both sides of every HTTP edge.** The caller ships the client call AND the
   callee ships the matching route (same method, matching path shape).
6. **Direct env access only.** `process.env.X` inside the call's template
   literal, or a module-level `X = os.environ["X"]` in the same file as the
   call. No dotenv files, no config modules, no re-exports.
7. **Dockerfile base images.** TypeScript services: `FROM node:20-slim`.
   Python services: `FROM python:3.12-slim`. Infra runs stock images and has
   no source directory.
8. **Packaging & start law.** TypeScript: **npm**, entry `index.ts`, `npm
   start` runs `tsx index.ts`. Python: **pip** + `requirements.txt`; an HTTP
   service starts with `uvicorn app.main:app --host 0.0.0.0 --port <port>`, a
   pure worker with `python main.py`. No committed lockfiles. The database
   wire uses the `postgresql://` scheme (the legacy `postgres://` alias is
   rejected by SQLAlchemy 2.x). Each service's per-service Packaging block
   below states its exact manager, manifest, start command and runtime.

## docker-compose.yml (produce this file verbatim at the repo root)

```yaml
services:
  gateway:
    build: ./gateway
    ports:
      - "3000:3000"
    environment:
      API_URL: http://api:8000
    depends_on:
      - api

  api:
    build: ./api
    environment:
      DATABASE_URL: postgresql://app:app@postgres:5432/ticketing
      REDIS_URL: redis://redis:6379
    depends_on:
      - postgres
      - redis

  worker:
    build: ./worker
    environment:
      REDIS_URL: redis://redis:6379
    depends_on:
      - redis

  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: ticketing
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app

  redis:
    image: redis:7
```

## Service `gateway` (ts / express)

Directory `./gateway`. Dockerfile first line: `FROM node:20-slim`.
Minimal skeleton: an express app (`app.use(express.json())`) listening on port 3000, plus `app.get('/health', (_req, res) => res.json({ ok: true }))`.

### Packaging

- Package manager: **npm**. No committed lockfile — `npm install` resolves
  the ranges in `package.json` at build time.
- Dependency manifest: `package.json` with `"scripts": { "start": "tsx
  index.ts" }` (the entry file is always `index.ts`).
- Start command: `npm start` (runs `tsx index.ts`).
- Runtime: `node:20-slim` (the Dockerfile base image; the container `CMD`
  is `["npm", "start"]`).

### HTTP clients to write

- `GET /tickets/*` against `api` via env `API_URL`:

  ```ts
  const r = await fetch(`${process.env.API_URL}/tickets/${p1}`);
  ```
- `POST /tickets` against `api` via env `API_URL`:

  ```ts
  const r = await fetch(`${process.env.API_URL}/tickets`, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify(payload),
  });
  ```

  The `method: 'POST'` property must be an inline literal in the call's
  options object.
