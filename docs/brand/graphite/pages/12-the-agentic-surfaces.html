Sheet 12 · The agentic surfaces

Ask, tools and the agentic run

Chat is the left column of the workspace and it drives the canvas. Everything the assistant knows came from the repo, and everything it did is on the record as a line you can read in one pass. This sheet fixes the four surfaces that record carries: the two message lanes, the tool row, the composer, and the gate at the end of a run.

Two asymmetries do the whole job. The user speaks in a box; the assistant does not. A request is short, so it can afford a bubble inset from the right; an answer carries prose, diffs, cards and paths, so it is plain full-width text with no bubble, no avatar and no role marker. And work is quieter than talk: a tool call is one 26px muted line, never an expanded log. The model shows its work; it does not perform it.

The circular filled send button is the signature element — 28px, --r-full, --accent-solid, an up arrow inside it. It is round, not a square with soft corners, and on most screens it is the only saturated object present.

Live V3 chrome (Decision 23–24) keeps that gold voice on a fill-screen macOS glass frame: quiet tabs, a gold thinking HUD while a turn is in flight, and frosted controls that share the book’s --glass-* recipe rather than inventing a second one.

Why the assistant gets no marker

A 2px accent bar down the side of every assistant message would put a gold object next to every paragraph in the thread, and the accent would immediately stop meaning anything except "a message exists". gold is the product's own voice — send, selection, focus. The send button and the canvas selection ring are the two places it is allowed to be loud, and both lose their only source of contrast the moment the transcript starts spending it. Law 2 kills the role marker before the bubble question is even asked.

The bubble survives on the user side alone because that is the side whose costs never come due: a request is a sentence, it never holds a diff, a graph or a file list, so the horizontal measure a bubble spends is measure that lane was never going to use.

12.2

The tool row

26px · --t-12 · --ink-3 · past tense

Four slots, left to right: the glyph for what kind of work it was, what it did in the past tense, the identifier it did it to, and a right cluster carrying the outcome. Only the first two are compulsory. The verb on a landed row is past tense because by the time the row is a record the call has been made — and the record contains one line per call, never two.

Placement is inline. Rows render inside the answer flow — quiet, indented under the prose they justify, behind a left rule — not gathered into a detached trail block above or below the answer. A trail block separates the evidence from the sentence it supports; inline, the reader meets each row exactly where the claim it grounds was made. Everything else about the row carries over unchanged: four slots, 26px, and the closed hue ledger of §12.7.

While a call runs, the row is alive and named. The live row takes the same four-slot chassis but speaks the present progressive — Searching ‹query›…, Reading ‹file›…, Planning… — with the pulsing-glyph treatment extended across the text as a shimmer. It exists only while the send button shows stop (§12.4), and when the call lands it is replaced, never appended to, by the past-tense row. A static pulse reads dead; a shimmering named status reads like work being done.

A row is one short clause. A tool whose row cannot be written in one short past-tense clause is a tool doing two things. Anything wider than the row becomes a right-hand affordance that opens the canvas or the index rail — never an expanded block inside the transcript.

12.3

The vocabulary of work

four groups · one glyph per kind of work

These are the events the ask stream actually emits, grouped by what the reader is being told: what was looked at, what was worked out, what was changed, and what was run. A group is not a category for its own sake — it is the answer to "how much should I care", and the order is cheapest first. Adding a tool to the product means adding a row here. Per §12.2, every row below renders inline in the answer flow, not in a detached trail block.

Two hues in the whole group, on a 14px glyph each: --fits for a command that returned zero and --wont for one that did not. The exit code stays a placeholder because the row's own tick already says which way it went — the number is for the reader who wants the detail, not for the verdict.

The shipped step labels are present-progressive and must be rewritten. The ask stream currently renders "Planning next moves…", "Searching the repo…" and "Drafting answer…" — a live status line, which is the correct shape while a step is in flight and the wrong shape the instant it lands. The rule is one string per step in each tense. The progressive form belongs to the live row, which exists only while the send button is showing stop (12.4); it is replaced by the past-tense row when the step lands, never appended to, so the record contains one line per call and never two. Decision 7 adds two things to that live row and takes nothing away: it shimmers (the pulse extended across the text, not the glyph alone) and it is named from the actual call — grounded verbs from the tool in flight, never a generic "Working…".

The placeholder is an instruction, not an invitation

"Ask about this repo — @ to reference a node, a file or a function." It names the one affordance a person cannot discover by looking, in the one place they are guaranteed to read, and it says what the assistant is grounded on in the same breath. It claims nothing that does not exist — a placeholder advertising an affordance the product lacks would be the product lying in its most-read line. Decision 4 (2026-08-24) added slash commands, so the line names / as well: it is precisely an affordance that cannot be discovered by looking. Two markers, and no more without a decision — this line is worth reading only while it is short enough to be read every time.

12.5

The run

queued · running · done · error · paused

A workflow is a graph of steps the scheduler walks, and the transcript shows it as run rows rather than as a wall of log output. Five states, each an alias (--st-*) rather than a verdict token, so what a state is worth is decided once. Every state is written out as a word as well as drawn as a dot, and the word carries the hue too: no state in this product is communicated by colour alone.

‹step›waiting on ‹step› Queued

Five rows, four hues, and the fifth state spends none — queued is --st-neutral, drawn as a hollow dot, because "not started" is not a claim about anything. Running is the only animated object on the surface, and it pulses rather than spins: a spinner says "wait", a pulse says "still true".

Nothing reaches the disk without a step you can see and approve. The write step opens as one plain line with icon buttons and a closed disclosure; the file list and the dry run live behind it. The card is dismissible, and dismissing it writes nothing.

One .btn.solid on the card, on the only action that commits something. Show details is closed by default and the dismiss control is an ic-x in the header, not a red button: a destructive or declining action in this design is worded, never reddened.

12.6

The gate

grounded · rejected · could not run

A gate is a deterministic verifier, not a second model grading the first. It takes the ids the agent claimed and checks them against the real attached graph; it commits or it rejects, and it never guesses. That is what makes the outcome worth a hue at all — and it is why there are three outcomes and not two.

Three cards, three badges, one chassis. The attempt ledger under the first two is drawn as dots so the count beside it is something the reader can check by looking — one dot, one attempt. The third card has no ledger because nothing was attempted.

Do
Could not run no graph attached

A gate that never had its input is --unknown — not known, and refusing to guess. It comes with the action that would make it runnable.

Don't
Failed no graph attached

Red means the check ran and the answer was no. Painting a missing prerequisite red teaches the reader to distrust every other red on the screen, which is the only defence the product has.

This is the same ruling the board makes about a connector it could not confirm: a claim the source could never check has not failed at anything. Unverified is --unknown in the transcript and --flow-declared on the canvas, and those two are the same token wearing two names on purpose.

12.7

The hue ledger for this sheet

eight tokens · six of them chromatic

Every token that carries colour on these surfaces is listed below with the claim it makes. Nothing outside this table is coloured: not a divider, not a heading, not a border, not a tool row, not a message lane, not the composer's chrome. Render the sheet in greyscale and no state becomes ambiguous, because every one of them is a word before it is a colour.

Eight rows and six actual hues: --unknown and --st-neutral are grey, which is the whole point of both. A greyscale render of this sheet therefore loses six colours and no meaning. Count the coloured objects in §12.1 while you are here: five, in an entire two-turn conversation — a Measured provenance tag, the .stat-add / .stat-del pair on the edited file, the tick on the command that returned zero, and the Grounded verdict. Four of the five are --fits and the fifth is --wont; every one of them is a claim about whether something ran and what it proved, and not one of them is chrome. That is the budget working — and the count is written out rather than gestured at, because a sheet whose own literal does not survive being counted has broken law 4 on the page that states it.

The inline fold (§12.2) adds zero rows to this ledger. Indentation, the left rule and the quieter ink of an in-flow row are chrome, and chrome is never coloured; the live row's shimmer animates the same --ink-3 the landed row prints at, so a working row and a finished one differ in motion and tense before either differs in colour. A running call earns no hue — it is not a verdict until it lands.
