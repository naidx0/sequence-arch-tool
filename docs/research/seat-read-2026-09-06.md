## The kill number did not fire, and two thirds of it could not

> *Not worth it if any same-build beat's snapshot differs across runs after ids are stripped, or if
> the snapshot costs more than 200 ms a beat, or if the replay's text diff is empty where the pixels
> differ.*

Only the middle condition was measurable tonight. The first needs **two** runs on one build and only
one completed; the third needs the replay, which never ran because the window stops a stage on a
non-zero exit and the seat exited 2. **"The kill did not fire" is therefore a weaker statement than
it looks**, and an unfired kill whose conditions were never measured is not evidence of safety.

## What the run found — and my first reading of it was wrong

I reported to the orchestrator that the seat never selects teach mode. **That was wrong.** The
turn's own work list, in `chat.json`, opens with:

```json
{"id": "step:teach-mode", "status": "done", "verb": "Taught this as a lesson"}
```

Teach mode was on. What is missing is the lesson:

- `.sequence/sessions/session-2999/` holds `chat.json` (3,518 bytes), `canvas.json` (65 bytes,
  `charts: 0`) and `meta.json` — and **no `lesson.json`**.
- With no lesson there is no concept, so `buildConceptChart` is never reached, so no chart is drawn,
  so no check-in is derived — and the model closed with *"Does this make sense so far?"*, a
  **clarifying** question the teach contract bans.

That single absence explains all three DIFFs at once. Beats 3, 7 and 9 are not three faults; they
are one.

## Not a regression from this night's work

Of 12 non-bench sessions, 4 hold a lesson and 8 do not — and the ones that do not include
`session-3105` and `session-3688` from **2026-09-05**, before any of tonight's changes. The four
that do (`live-check-69`, `seat-4173`, `brief-rerun`, `session-5305`) were all created with an
**explicit thread id**; the UI-created `session-NNNN` ones mostly were not.

**The leading hypothesis, labelled as one:** `packages/web2` sends no `threadId` on an ask (a grep
finds none), so `resolveAskThreadId` falls back to `index.activeId`; when that does not name the
session the UI is displaying, `beginTeachTurn` has no thread, `lesson` is `undefined`, and
`finish()` returns before writing anything. The index agrees — `activeId` is `session-3391` while
the seat's conversation is `session-2999`.

**It is a hypothesis, not a finding.** Confirming it needs a request against a running app, which is
a provider call, and the card is another lane's. What is established without a run: teach mode was
on, no lesson was written, no UI-created session tonight has one, and sessions given an explicit
thread id do.

## The void, and what it was really about

> *reload: the conversation changed across a reload, which is not what a reload claims*

`chat.json` before and after the reload: **same 3,518 bytes, different sha256**. Parsed and compared
field by field, **zero fields differ** — the bytes diverge at offset 630, where one `work` step is
serialised with its keys in a different order (`status, outcome, group` against `group, verb, …`).
1,177 bytes differ; no content does.

So the void is right about the file and wrong about the conversation: **the seat hashes bytes where
it means content.** The remedy is not to relax the check but to hash the parsed document, which
still catches a genuine change and stops calling a re-serialisation a changed conversation.

That the server rewrites `chat.json` with unstable key order is worth its own look, but it is not
what the void claimed.
