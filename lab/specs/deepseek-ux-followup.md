## T3 local bridge: distinguish official runtime from third-party CLI

Official **T3 Code** is [`pingdotgg/t3code`](https://github.com/pingdotgg/t3code), whose root [license](https://github.com/pingdotgg/t3code/blob/main/LICENSE) is MIT, copyright 2026 T3 Tools Inc. Its [internals overview](https://github.com/pingdotgg/t3code/blob/main/docs/internals/overview.md) places durable domain events/projections and an outbox ahead of worker execution. Turn completion is separate from later run finalization: late housekeeping need not keep the answer visibly busy. Apply that boundary to Sequence rather than importing T3's orchestrator.

Its [provider architecture](https://github.com/pingdotgg/t3code/blob/main/docs/internals/providers.md) separates adapters, instance ownership and probing; provider diagnostics are deliberately bounded/sanitized. Its [Claude guide](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-claude.md) uses Claude Code's existing local login/config and notes that usage limits can keep a run waiting. Thus Sequence must distinguish a known rate-limit wait from an unexplained stall, and must not equate bridge presence with ready authentication. No local login/config was inspected.

The separate [`MajesteitBart/t3code-cli`](https://github.com/MajesteitBart/t3code-cli) is **third-party**, not proof of an official T3 CLI API. Its [README](https://github.com/MajesteitBart/t3code-cli/blob/main/README.md) documents an external client for a running T3 server: discovery/doctor, explicit busy-message policy, thread read/wait and handover. It checks protocol compatibility before sign-in; it also distinguishes creating an exact thread from merely revealing the desktop window. Those are useful bridge UX contracts. Its license was not independently read, so no copying/license claim is made for this repository. No installation, doctor/auth invocation, server discovery, npm command or local token read occurred.
